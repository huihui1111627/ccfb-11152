# 实现说明：关键决策与取舍

本文记录文档（docs/rules.md、docs/api.md）之外的设计决策、踩过的坑，以及为什么这么做。

## 1. 为什么“高周期由 1m 聚合”而不是“每个周期各自切成交”

最初考虑对每个周期直接从逐笔切窗（更“快”）。放弃了，原因：

- **一致性无法自证**。用户的核心痛点是“自己合的 K 线总和行情软件对不上”。如果 1m、5m、日线各切各的，
  一旦窗口边界或竞价归属有细微差异，跨周期就对不上，而且很难定位是哪一层错了。
- 改成“1m 是唯一真源，其余全是聚合”，`Σ1m == Σ5m == … == 1d` 就成了结构性保证（R70），
  `/api/consistency` 每次都能全绿。聚合只做 OHLC 的 `open=首、close=尾、high/low=极值` 与量额求和，
  没有歧义。

代价：高周期残 bar（如期货 30m 的 `(10:00,10:15]`）要由 1m 标签映射到高周期窗口，
多了一层 `label_window`。这个映射是纯函数，测试覆盖了 A 股 241/48/16/8/4 与期货 345/69/23/12/7 的窗口数。

## 2. 时间戳：为什么用“本地时间戳”

所有 `ts` 都是**把本地时间当 UTC** 换算的 epoch 毫秒（等于真实 epoch 减 8 小时）。
这样：

- Rust 侧 `NaiveDateTime.and_utc()` 就是唯一换算，不需要时区库、不受夏令时影响；
- 前端 `new Date(ts).getUTC*()` 直接得到交易所本地时间，**不需要任何时区转换**；
- JSON 里不会出现“09:30 还是 01:30”的歧义。

唯一的坑是**不能用 `getHours()`**（会按浏览器时区偏移）。前端统一用 `getUTC*`，见 `web/assets/chart.js`。

## 3. 集合竞价的两种挂靠方式

A 股与期货的竞价成交时间戳位置不同，导致归属规则必须分开：

- **A 股开盘竞价**成交在 `09:25:00`，早于连续竞价起点 `09:30`。如果只靠“落在哪个 1m 窗口”来判定，
  它会落到一个不存在的窗口里。所以显式生成一根 `label=09:30`、`auction_only=true` 的窗口，
  窗口本身是 `[09:15, 09:25]`，只接受竞价成交。
- **期货开盘竞价**成交恰在 `09:00:00`（或 `21:00:00`），正好是连续段首。
  按“段首左闭”，它自然落进 `09:01`（或 `21:01`）bar，不需要额外窗口。
- **A 股收盘竞价**成交在 `15:00:00`，正好是连续网格（延伸到 15:00）的最后一格右端点。
  这一格标记为 `auction_only`：只接受竞价成交，14:57–15:00 的连续成交判 `out_of_session`。

`auction_only` 这个字段就是为“同一时间窗内只允许某类成交”而加的。

## 4. 冲正账本：为什么不用“减去量额”的增量更新

增量更新（撤销时 `v -= vol`）看起来简单，但 OHLC 无法增量维护——撤销的可能是最高价那笔，
`high` 必须回落到剩余成交的最大值。所以每根 1m bar 维护**有效成交列表**，冲正后整根重算
（`recompute`），再由 1m 重新聚合到高周期。

重算的正确性依赖“按消息序号顺序取 open/close”（R21），而不是按到达顺序：
更正可能把成交移动到另一个 bar，序号顺序才是“这笔成交在原始时间轴上的位置”。

踩过的坑：`correct_trade` 会保留一份“失效的旧副本 + 有效的新副本”。
之后若再来一次冲正，**按 trade_id 线性搜索会命中旧副本**（已失效），导致重复扣减或扣错。
修法是 `DayLedger.index: trade_id -> (slot_idx, trade_idx)`，冲正时按索引精确定位，
并留一个“索引失配则搜有效副本”的兜底。`mk-engine/tests/reversal_edge.rs` 固化了这个场景。

## 5. 多源合并：为什么只在“主源有缺口”时补数

最初的实现是“B 源里 A 没有的 trade_id 全都并进来”。结果是某些 bar 的量偏大：
B 源偶尔会收到 A 源根本没有的成交（真实场景里可能是两路行情的时间窗差异）。
这些成交并入后，`Σ1m` 与日线仍然一致（都是合并后算的），但**与只订阅 A 源的行情软件对不上**。

改成 R51：只有主源 `A` 出现**序号缺口**（`seq` 跳号）时，才在缺口的时间窗 `(prev_ts, next_ts]` 内
用对源补数。没有缺口就说明 A 源数据完整，B 源的“额外”成交不属于本次合并。

交叉校验器 `tools/crosscheck.py` 也复刻了这个逻辑，否则会多算（这是它早期差异的主要来源）。

## 6. 异常隔离的副作用：参考价不更新

`price_jump` 的判定依赖“上一笔有效成交价”。如果坏点更新了参考价，后续所有正常成交都会相对坏点
偏移，导致连锁误杀（R42 明确禁止）。同理，滚动量窗口也不纳入被隔离的成交。

另一个坑：**时间戳倒挂的判定只能与紧邻前一条比较，不能与运行最大值比较**。
早期实现用了运行最大值，结果一条倒挂消息之后的正常消息全部被判为倒挂（15k+ 误报）。
改成“与前一条比较，倒挂后把基准下移到当前消息”——只报越界的那一条。

## 7. 成交量异常：竞价与首笔

两个必须排除的场景：

- **集合竞价成交不参与量异常判定**。竞价是一次性撮合，量天然是连续竞价的几十倍；
  不排除的话每个交易日的竞价都会被隔离（实测误报 33 条 → 0 条）。
- **滚动窗口不足 8 笔时，绝对下限仍然生效**。早期实现在样本不足时直接 `return None`，
  导致开盘前几笔的超大坏量漏检。R44 的阈值是 `max(绝对下限, 100×中位数)`，
  样本不足只影响中位数项，不该关掉绝对下限。

## 8. 仿真器的异常注入：顺序很重要

注入器最早是“随便改字段再重排”，结果注入的缺口被重编号填平、倒挂被排序抹掉。
现在的顺序是：

1. 内容修改（价格/量/tick/涨跌停/时段）——只改字段；
2. 插入消息（撤单/更正/废单/停牌成交/未知撤单）——按 ts 插入，seq 置 0 由后续统一编号；
3. 整源按 ts 稳定排序 + 连续编号（此时源内时间单调、序号连续）；
4. **破坏顺序的注入**：时间戳倒挂、同序号重复、删消息制造缺口——必须最后做。

注入的“真值”写进 `dataset.json.injected_anomalies`，`/api/injections` 用它算召回率。
当前数据集 88/88 全部命中。

## 9. 交叉校验：独立实现的价值

`tools/crosscheck.py` 完全不复用 Rust 代码，按规则独立实现窗口切分、竞价归属、交易日归属、
多源合并、冲正、异常隔离，再从原始 JSONL 重新聚合 1m，与 `/api/bars` 逐根比对。

- 无冲正/无倒挂的交易日（如 2026-03-06）：**全部品种 0 差异**。
- 有复杂时序的交易日：0–2 根 bar 差异，均来自多源合并后事件的精确排序（引擎用全局重排 seq，
  脚本用原始 seq）。这是已知不覆盖项，在脚本头部注明了。

这个脚本存在的意义：证明“标准答案”不是引擎自己算出来再自己核对。它也反过来发现过引擎的问题
——比如它早期把注入的跳变价当作 open，恰好说明引擎的隔离是对的。

## 10. 连续合约：以最新合约为基准

主力切换时，老合约与新合约的价格天然不同（rb2601 3959 vs rb2605 3617）。连续序列必须复权，
否则切换处会出现一个假跳空。

采用的方案是 R62：`ratio = close_new(d-1) / close_old(d-1)`，切换日之前的 bar 全部乘以该 ratio，
使序列以最新合约为基准。实测切换处跳空 0.14%（就是正常的隔夜波动幅度），而不是 8.6%。

为什么不“以老合约为基准向后复权”（即调整切换日之后的价格）？因为连续合约的主要用途是
“看最新合约口径的历史”，以最新为基准更符合直觉，且不会让最新价为 1.0 倍以外的系数。

## 11. 未做的与刻意的简化

- **不做主动买卖推断**（R12）：以交易所逐笔方向为准。很多软件会按 tick 规则推断，
  那会造成“同一笔成交在不同软件里 B/S 不同”，本引擎不做这件事，也就少一个对不上的来源。
- **不做复权对成交量的调整**：成交量不发生除权变化（R31）。
- **期货不适用复权**：请求 forward/backward 直接返回 400 `adjust_not_supported`（R33），
  前端下拉框对期货禁用。
- **批处理而非流式**：引擎先合并全部消息再回放。好处是迟到冲正天然正确（账本可回溯重算），
  代价是内存与启动时间（95 万条约 10 秒）。
- **仿真数据规模**：默认 6 个交易日 / 7 个合约 / 约 96 万条消息，是“能跑完、能看清”的折中，
  不是生产级吞吐基准。
