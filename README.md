# 充电桩运营 SLO 管理平台

面向充电桩运营后台(几十个微服务)的服务级目标管理平台。接入各服务上报的请求指标,
计算**可用性**与**延迟分位**两类 SLO,基于 Google SRE 的**多窗口多燃烧率(MWMB)**做告警,
实时跟踪**错误预算**并驱动**发布闸门**,同时提供与固定阈值告警的量化对比评估。

技术栈:TypeScript 全栈,**零运行时依赖** —— 后端用 Node 内置 `node:http` + `node:sqlite`,
前端原生 TS + 手写 SVG 图表,无框架、无 CDN、无原生模块。

---

## 快速开始

```bash
npm install
npm run simulate   # 1. 生成 30 个服务 × 181 天 × 5 分钟桶的模拟指标(约 156 万行,含 16 个注入故障)
npm run evaluate   # 2. 流式回放,跑 MWMB 与固定阈值两套检测器,产出对比报告
npm run build:web  # 3. 编译前端 TS
npm run dev        # 4. 启动 http://localhost:3000
```

其它命令:`npm run typecheck`(前后端类型检查)、`npm run reset`(清空数据重来)、
`npm run build`(编译前后端生产产物,之后 `npm start` 用纯 node 运行)。

## 八项需求的实现位置

1. **好请求/总请求口径,可用性 + 延迟分位,滚动 28 天 / 自然月**
   - 类型 `src/shared/types.ts`;窗口聚合 `src/slo/window.ts`;SLO 定义 `src/config/catalog.ts`
   - 可用性 good = 非错误请求;延迟 good = 成功请求中延迟 ≤ 阈值的请求(直方图 `countBelow`)

2. **多窗口多燃烧率告警(短+长窗口同时超阈值)**
   - 判定纯函数 `src/slo/alerting.ts` 的 `evaluateBurnRule`;状态机 `src/slo/stream.ts`
   - 三档规则:fast(5min/1h,14.4x)、medium(30min/6h,6x)、slow(2h/72h,3x/1x)
   - 额外加了**恢复迟滞(0.85x)与 30 分钟重报冷却**,解决阈值边界 flapping(详见下文踩坑)

3. **错误预算剩余量、消耗速度、耗尽预测**
   - `src/slo/budget.ts`:近 1h 与近 24h 两个速度分别线性外推 ETA

4. **预算低于阈值自动拦截非紧急发布;紧急发布填理由留痕**
   - `src/slo/gate.ts`;阈值可在页面调整;四条判定路径均有测试覆盖

5. **依赖关系图下游 SLO 受上游影响标记**
   - `src/slo/impact.ts`(传递上游分析 + 爆炸半径);前端 `src/web/pages/graph.ts`

6. **区分无数据与真故障**
   - 缺口桶(`reported=0`)不计入 SLO 分母,单独统计 `gapBuckets`;独立缺口检测器,
     燃烧率规则在窗口含缺口时跳过判定(`src/slo/alerting.ts`)

7. **计划内维护窗口从预算排除**
   - 按桶与维护窗口的时间重叠比例从分母剔除(`aggregateWindow`)

8. **SLO 历史达标按周导出**
   - `src/slo/compliance.ts`,UTC 自然周切分,页面服务详情内可下载 CSV

## 模拟数据与故障注入

`src/simulate/`:确定性 RNG(同种子可复现)、昼夜流量模式、对数正态延迟直方图、
依赖边错误传导。16 个故障覆盖四类:

- **突发全挂**(5 个):支付、核心库、会话、缓存、鉴权,20~90 分钟近全挂
- **缓慢劣化**(4 个):慢 SQL / 连接池泄漏 / 消息积压,24~60 小时爬升
- **上报中断**(4 个):采集 Agent / 管道故障,服务本身正常仅指标缺失
- **错误尖峰**(3 个):15~30 分钟短抖动,专门考验误报

## 评估结论(本次数据)

| 检测器 | 告警数 | 误报 | 漏报故障 | 平均检测延迟 | 精确率 | 召回率 |
|---|---|---|---|---|---|---|
| **MWMB 多窗口燃烧率** | **171** | 145 | **0** | 222 min | 15.2% | **100%** |
| 固定阈值 5%(对照) | 2533 | 2419 | 0 | 260 min | 4.5% | 100% |
| 缺口检测 | 8 | 0 | 0 | 25 min | 100% | 100% |

- MWMB 告警量比固定阈值**减少 93.2%**,召回率持平(12 个真实故障全检出)
- 缓慢劣化场景 MWMB 优势最大:如 kafka-bus 故障 MWMB 520 分钟发现,固定阈值 1540 分钟
- 4 个上报中断全部由缺口检测器在 25 分钟内识别,**未产生任何虚假故障告警**
- 固定阈值在夜间小流量桶噪声极多;MWMB 的双窗口确认天然过滤这类毛刺

> 精确率数字偏低是因为评估把"故障窗口外的一切告警"都算误报,而高扇入 BFF 在故障
> 传导余波里的燃烧告警其实是真问题,只是没被标成故障。这是评估口径的保守性,不是检测器缺陷。

## 开发中真实踩过的坑(都已修复并体现在代码里)

1. **滚动窗口未满就参与判定** → 回放初期少量错误桶算出虚高燃烧率,告警风暴。加 `full` 标志。
2. **阈值边界 flapping** → 燃烧率在阈值附近噪声抖动导致每桶触发/恢复。加迟滞 + 冷却。
3. **健康基线本身超 SLO 允许线** → 基线错误率 1‰ 配 99.9% 目标,健康期就在"燃烧"。基线按 SLO 比例重设。
4. **依赖传导线性求和爆炸** → 多层扇入把网关健康错误率推到 1.1%。改独立事件概率并 + 收紧调用占比。
5. **延迟 SLO 阈值比健康 p95 还严** → 健康即违约。阈值取健康 p95 的 ~1.3 倍,目标按真实表现定。
6. **双重缩放 bug** → 延迟达标率被连除两次只剩 11%。改为比例迁移口径。

这些正是真实 SLO 落地最常见的错配,代码注释里都有对应说明。

## 目录结构

```
src/
  shared/      领域类型与时间工具(前后端共享)
  config/      服务目录、SLO 定义、告警策略、故障/维护计划
  db/          node:sqlite 建表、索引、种子数据
  simulate/    确定性 RNG、依赖图、指标生成器、落库编排
  slo/         直方图、窗口聚合、预算、告警、闸门、依赖影响、周报
  evaluation/  双检测器回放与对比报告
  api/         HTTP 路由与静态服务
  web/         原生 TS 单页应用(编译产物 *.js 同目录)
```
